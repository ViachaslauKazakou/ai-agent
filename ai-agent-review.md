# Анализ реализации ai-agent (ViachaslauKazakou/ai-agent)

Репозиторий: https://github.com/ViachaslauKazakou/ai-agent
Крейт находится в корне репозитория, Rust edition 2024.

Проанализированы: `agent.rs`, `tools.rs`, `llm.rs`, `index.rs`, `agents.rs`, `main.rs`, `domain.rs`, `word_processing.rs`.

## Баги

### 1. Паника на UTF-8 при обрезке результатов

Везде используется `String::truncate(bytes)`:

```rust
let truncated = result.len() > context.max_result_bytes;
if truncated { result.truncate(context.max_result_bytes); }
```

`truncate` паникует, если индекс не на границе символа. Любой файл с кириллицей/эмодзи длиннее `max_result_bytes` роняет процесс. Затронуты `ReadFile`, `ListDirectory`, `SearchFiles`, `RunCommand`. В `llm.rs::truncate_for_error` сделано правильно (через `chars().take()`) — стоит применить тот же подход везде, либо использовать `floor_char_boundary`.

### 2. Ephemeral-результаты ломают следующий запрос

В `agent.rs` assistant-сообщение с `tool_calls` кладётся в сессию всегда, а tool-результат — только при `persist`:

```rust
let (content, persist) = match result { Ok(r) => (r.content, !r.ephemeral), ... };
self.push_tool_result(session, &call.id, content, persist);
```

Почтовые инструменты возвращают `ephemeral: true` → в `.agent-session.json` остаётся `tool_calls` без парного `tool`-сообщения. На следующем запросе история восстанавливается из сессии, и OpenAI-совместимый endpoint возвращает 400 (`messages with role 'tool' must be a response to a preceding tool_calls`).

**Фикс:** сохранять плейсхолдер (например, `[содержимое письма не сохранено]`) вместо полного пропуска сообщения.

### 3. Исчерпание `max_tool_rounds` уничтожает ответ

Цикл заканчивается `Err(AppError::ToolRoundLimit)`, весь раунд теряется.

**Фикс:** на последней итерации отправить запрос без `tools` и вернуть то, что модель написала, пометив результат как `truncated`.

### 4. Пустой content → потеря ответа

`Message::new` отвергает пустую строку, а в `agent.rs` результат прогоняется через неё: если модель вернула `content: ""` с `finish_reason: "stop"`, получаем `AppError::EmptyMessage` вместо корректного завершения диалога.

### 5. `run_command`: allowlist только по имени бинаря, нет таймаута

`command_allowlist = ["git"]` разрешает `git push --force`; `["make"]` или `["sh"]` — фактически выполнение чего угодно. Плюс `child.output().await` без таймаута: зависшая команда вешает агента навсегда, `Ctrl-C` в REPL не обрабатывается.

**Нужно:** таймаут на выполнение, лимит на размер stdout до чтения в память, allowlist в виде (команда, разрешённые подкоманды/паттерн аргументов), а не просто имя.

### 6. Нет deny-list на чтение

`.env`, `.git/config`, `*.pem`, `id_rsa` внутри `working_dir` читаются свободно и уходят в LLM. Проверка пути защищает только от выхода за пределы каталога, не от чувствительных файлов внутри него.

### 7. Недетерминированный порядок tool definitions

`ToolRegistry` построен на `HashMap` → `definitions()` каждый раз возвращает разный порядок. Это ломает prompt caching на стороне провайдера и делает поведение невоспроизводимым.

**Фикс:** `BTreeMap` или `IndexMap`.

## Архитектурные замечания

### Нет редактирования файлов, только перезапись

Для кодингового агента это главное ограничение. `write_file` заставляет модель регенерировать файл целиком — дорого по токенам, и модель регулярно теряет куски при больших файлах.

**Нужно:** `edit_file(path, old_str, new_str)` с требованием уникального совпадения (по аналогии с str_replace) и `apply_patch` для unified diff. Заодно `confirm_writes` станет осмысленным: можно показывать diff перед подтверждением, а не голое «Разрешить запись? [y/N]».

### Нет управления контекстом

`self.messages` растёт неограниченно, каждый tool-результат (до 50 КБ) попадает в историю и переотправляется в каждом раунде. Плюс `self.messages.clone()` на каждой итерации цикла — O(n²) по аллокациям. На реальном репозитории уже 3–4 вызова `read_file` могут вынести окно контекста.

**Минимум:**
- бюджет токенов на историю;
- схлопывание старых tool-результатов в `[N строк, вытеснено]`;
- автокомпакция истории через summary-запрос при достижении ~70% окна.

`Usage` уже собирается в коде — его стоит использовать для бюджета, а не только для статистики в REPL.

### Поиск по проекту неэффективен

`SearchFiles` рекурсивно обходит `.git` и `target` — на типичном Rust-проекте это десятки тысяч файлов и гигабайты данных.

**Фикс:** крейт `ignore` (уважает `.gitignore`) + `grep-searcher`/`regex`, ограничение числа совпадений на файл.

`ProjectSearch` на каждом вызове делает `load → update() → save()`: полный обход дерева и перезапись всего JSON-индекса. Сам индекс хранит полный текст всех чанков, то есть по сути дублирует репозиторий в `index.json`. Скоринг — количество уникальных терминов запроса в чанке, с `format!` + `to_lowercase()` на каждый чанк при каждом поиске. `hash` считается, но для инвалидации не используется (сравниваются только `size` + `modified_secs`).

**Фикс:** инвертированный индекс (токен → id чанков), BM25-скоринг, хранение offsets вместо полного текста, обновление индекса не чаще, чем раз в N секунд, а не на каждый вызов.

### Параллельные tool-вызовы

Модель может вернуть за один раунд сразу несколько вызовов (например, 5×`read_file`), но они выполняются последовательно.

**Фикс:** для read-only инструментов — `futures::future::join_all`, с сохранением порядка результатов по `tool_call.id`.

### Нет стриминга и нет отмены

Ответ печатается целиком после завершения генерации, длинный ответ нельзя прервать.

**Фикс:** `stream: true` + SSE-парсер на стороне клиента; `tokio::select!` с `ctrl_c` вокруг `agent.complete` в REPL (в scheduler это уже сделано, а в REPL — нет).

### REPL блокирует рантайм

REPL читает stdin блокирующе (`stdin.lock().read_line`) внутри `#[tokio::main]` — это блокирует поток рантайма. Также нет истории команд и редактирования строки.

**Фикс:** `rustyline` или `reedline`, либо как минимум `spawn_blocking` для чтения ввода.

### Retry / обработка ошибок провайдера

Нет backoff на 429/503, нет обработки `Retry-After`. Заявленный в README fallback после HTTP 400 из-за неподдерживаемых tools делается относительно тривиально: детектить в теле ошибки упоминание tools и повторить запрос один раз без `tools`.

### Skills грузятся целиком в system prompt

При росте числа skills это постоянный оверхед токенов на каждый запрос.

**Фикс:** прогрессивное раскрытие — в промпт помещать только `name: description`, а полное содержимое подгружать через отдельный tool `read_skill(name)`.

### Память проекта отсутствует

Сейчас памяти как таковой нет — сессия это просто лог сообщений. Минимальный набор для цели «чтобы модель понимала контекст проекта»:
- автоподхват `.aiagent/AGENTS.md` из корня репозитория в system prompt;
- tool `remember(key, text)`, пишущий в `.aiagent/memory/*.md`;
- summary после компакции контекста, сохраняемый в сессию.

## Мелочи

- `registry_from_names` дублирует `default_registry` — третье место для правки при добавлении нового инструмента. Лучше enum со списком `all()`.
- `ConfiguredProvider::new` молча подменяет `api_base_url` на localhost, если provider профиля отличается от provider в конфиге — лучше явное поле `base_url` в профиле агента.
- `.agent-session.json` пишется прямо в каталог анализируемого проекта: мусор в чужих репозиториях плюс содержимое файлов в открытом виде на диске. Логичнее `~/.local/share/ai-agent/sessions/<id>.json`.
- `word_processing.rs` выглядит как остаток учебного кода в публичном API.
- `LlmMessage::from_message` всегда ставит `content: Some("")` для assistant-сообщений с `tool_calls`; часть провайдеров это отвергает — нужен `None`.

## Приоритеты

Наибольший выигрыш на единицу работы дают:
1. `edit_file` вместо полной перезаписи файлов.
2. Управление/компакция контекста.
3. Исправление паник на UTF-8 truncate (быстрый фикс, критичный баг).
