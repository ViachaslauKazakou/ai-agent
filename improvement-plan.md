# План разделения CLI и Desktop и развития Desktop-приложения

## 1. Цель

Разделить пользовательские сценарии CLI и Desktop, сохранив единое ядро агента. CLI и Tauri должны быть тонкими адаптерами над общими Rust API: конфигурацией, проектами, сессиями, моделями, инструментами и политиками безопасности.

Desktop должен запускаться со стартового экрана, восстанавливать безопасные метаданные предыдущего запуска, предлагать недавние проекты и доступную для продолжения сессию, а затем открывать один из режимов: Chat-bot, Assistant, AI Tutor или Coder.

## 2. Текущее состояние и выявленные ограничения

- [x] Desktop использует общее Rust-ядро через `src/application.rs`.
- [x] Открытие проекта, загрузка моделей, создание сессии и чат уже доступны через Tauri.
- [x] Проектная конфигурация хранится в `.aiagent/config.json` и `.aiagent/providers.json`.
- [x] CLI умеет продолжать единственную проектную сессию `.aiagent/session.json`.
- [ ] Пользовательское состояние между запусками отсутствует.
- [ ] Desktop-проекты и сессии находятся только в памяти процесса.
- [ ] Стабильные идентификаторы проектов между запусками отсутствуют.
- [ ] Стартовый экран и навигация между режимами отсутствуют.
- [ ] `ListProjects` и `ListSessions` не дают данные после перезапуска.
- [ ] Создание нового каталога проекта не поддержано: открыть можно только существующий каталог.
- [ ] UI выбора файлов пока декоративный и не передает вложения агенту.
- [ ] Заявленный `via-agent --working-dir` не обрабатывается Tauri-приложением.
- [ ] Автотестов frontend нет; `npm run check` проверяет только синтаксис.

## 3. Архитектурные правила

1. **Единое ядро.** Бизнес-логика не переносится в Tauri или JavaScript.
2. **Разделение хранилищ.** Пользовательское состояние, проектная конфигурация и содержимое сессий имеют разные схемы и жизненные циклы.
3. **Безопасные метаданные.** Глобальное состояние не содержит API-ключи, OAuth-токены, сообщения, аргументы/результаты инструментов или содержимое файлов.
4. **Версионирование.** Каждый долговечный JSON-документ имеет версию схемы и определенное поведение для неизвестной версии.
5. **Атомарная запись.** Обновления выполняются через временный файл и атомарную замену.
6. **Инъекция путей.** Тесты используют временные каталоги и никогда не изменяют реальную домашнюю директорию.
7. **Обратная совместимость.** Существующая `.aiagent/session.json` рассматривается как legacy-сессия до введения много-сессионного формата.
8. **Тонкий frontend.** WebView получает DTO и вызывает команды, но не получает прямого доступа к пользовательскому хранилищу.
9. **Документация по этапам.** Каждый этап обновляет профильный документ, пользовательскую инструкцию и команды проверки.
10. **Комментарии по назначению.** Публичные Rust API документируются `///`/`//!`; комментарии внутри функций добавляются только для неочевидных гарантий и решений.

## 4. Целевая модель хранения

### 4.1 Пользовательское состояние запуска

Предпочтительное расположение определяется кроссплатформенным resolver-ом каталогов приложения. Если продуктово требуется файл непосредственно в home, используется документированное расположение `~/.ai-agent/state.json`, но путь все равно определяется без ручного чтения только `$HOME`.

Предварительная схема:

```json
{
  "schema_version": 1,
  "last_started_at": "2026-09-29T10:00:00Z",
  "last_project_id": "stable-project-id",
  "last_session_id": null,
  "projects": [
    {
      "id": "stable-project-id",
      "path": "/absolute/canonical/path",
      "last_opened_at": "2026-09-29T10:05:00Z",
      "last_session_id": null
    }
  ]
}
```

Ограничения:

- список ограничен по размеру;
- повторное открытие канонического пути обновляет существующую запись;
- отсутствующий каталог не удаляется молча, а помечается недоступным в DTO;
- поврежденный файл не перезаписывается без сохранения/явной диагностики;
- неизвестная будущая версия схемы отклоняется;
- секреты и история диалога запрещены.

### 4.2 Проектная конфигурация

Остается в `<project>/.aiagent`. В `Config` должны быть явно разделены:

- `project_dir` — каталог, которому принадлежат `.aiagent/config.json` и `.aiagent/providers.json`;
- `working_dir` — рабочий каталог инструментов агента.

### 4.3 Сессии

На переходном этапе поддерживается `<project>/.aiagent/session.json`. Будущий формат нескольких сессий проектируется отдельно: индекс, отдельные файлы, метки времени, заголовок, provider/model, миграция и политика удаления.

## 6. Порядок проверки и коммитов

После каждого этапа работа останавливается на контрольной точке:

1. Исполнитель отмечает завершенные пункты `[x]` и указывает измененные файлы.
2. Запускаются профильные тесты и общий минимальный quality gate.
3. Пользователю предлагается проверить функциональность и приведен manual checklist.
4. Коммит создается только после явной команды пользователя.
5. Следующий этап начинается только после проверки/решения пользователя.

Шаблон сообщения этапа:

```text
Этап N готов к проверке.
- Реализовано: ...
- Документация: ...
- Автопроверки: ...
- Проверьте вручную: ...

После проверки можно дать команду создать коммит и перейти к этапу N+1.
```

## 7. Общий quality gate

```bash
cargo fmt --all -- --check
cargo check --workspace
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
npm --prefix frontend run check
npm --prefix frontend run build
```

Для этапов без frontend-изменений npm-команды можно оставить общим regression gate; профильные Rust-тесты запускаются дополнительно.
