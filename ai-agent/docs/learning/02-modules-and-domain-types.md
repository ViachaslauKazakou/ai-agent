# Этап 2. Модули, структуры и предметные типы

## Цель

Разделить консольный запуск и библиотечную логику, а также описать минимальную
предметную область будущего агента через `enum`, `struct`, методы, собственный
тип ошибок и UUID-сессии.

Этап по-прежнему не подключает CLI-библиотеку, сеть, LLM или agent loop.

## Результат

```text
src/
├── main.rs
├── lib.rs
├── domain.rs
├── error.rs
└── word_processing.rs
tests/
└── public_api.rs
```

`main.rs` теперь только читает stdin, вызывает публичные функции библиотеки и
печатает результат. Это позволяет тестировать логику без терминала.

## Доменные типы

### `Role`

`Role` — enum с четырьмя вариантами:

- `System` — системная инструкция;
- `User` — сообщение пользователя;
- `Assistant` — ответ агента или модели;
- `Tool` — результат инструмента.

Тип уже получил `Serialize` и `Deserialize`, чтобы в следующих этапах его
можно было передавать в JSON без изменения модели данных.

### `Message`

`Message` содержит приватные поля:

```rust
pub struct Message {
    role: Role,
    content: String,
}
```

Поля закрыты, поэтому создание проходит через `Message::new`. Конструктор
проверяет, что сообщение не пустое. Методы `role` и `content` возвращают
заимствованные данные и не передают владение наружу.

### `Session`

`Session` хранит:

- `Uuid` — идентификатор;
- `PathBuf` — рабочую директорию;
- `String` — имя модели;
- `Vec<Message>` — историю.

Метод `add_message` принимает `Message` по значению. Это означает передачу
владения сообщением в сессию: после добавления сессия становится владельцем
элемента истории. Метод `messages` возвращает `&[Message]`, поэтому внешний
код может читать историю, но не может изменить её напрямую.

## Собственные ошибки

`AppError` находится в `src/error.rs` и использует derive `thiserror::Error`.
Сейчас есть три варианта:

- `EmptyInput`;
- `EmptyMessage`;
- `EmptyModel`.

Публичные функции возвращают `Result<T, AppError>`. Это лучше строковой ошибки
этапа 1: вызывающий код может сопоставлять варианты enum, а не сравнивать
тексты сообщений.

## Почему логика разделена

До этапа 2 все функции и тесты находились в `main.rs`. Для маленького примера
это допустимо, но `main` быстро становится неудобным местом для доменной
логики. Теперь:

- `lib.rs` объявляет и переэкспортирует публичный API;
- `domain.rs` содержит предметные типы;
- `error.rs` содержит ошибки;
- `word_processing.rs` содержит чистые функции слов;
- `main.rs` занимается только терминальным сценарием.

## Unit- и интеграционные тесты

Unit-тесты остаются внутри модулей под `#[cfg(test)]`. Они проверяют внутренние
детали конкретного модуля и находятся рядом с реализацией.

Интеграционные тесты находятся в `tests/public_api.rs`. Cargo компилирует
каждый файл из `tests/` как отдельный crate, поэтому эти тесты используют
только публичные элементы `ai_agent`. Так проверяется реальный контракт
библиотеки, а не её приватное устройство.
