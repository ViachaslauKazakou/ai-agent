# План реализации локального AI-агента

## 1. Цель проекта

Реализовать локальный аналог Cline / Aider / Claude Code с Rust-клиентом и возможностью подключать разные языковые модели через LiteLLM. Агент должен работать из терминала, понимать запрос пользователя, анализировать рабочую директорию, вызывать инструменты, изменять файлы только через контролируемые операции и возвращать итоговый ответ.

Основной принцип реализации: сначала построить надёжное ядро без UI, сложной автоматизации и multi-agent режима, затем постепенно добавлять удобства и расширения.

Целевая схема:

```text
CLI / REPL
   |
   v
Session: история, модель, рабочая директория
   |
   v
Agent loop: prompt -> LLM -> tool call -> result -> LLM -> answer
   |                                  |
   |                                  +--> read_file
   |                                  +--> write_file
   |                                  +--> list_directory
   |                                  +--> search
   |
   +--> LLM provider: LiteLLM / OpenAI-compatible API / Ollama
```

## 3. Цели MVP

В первую рабочую версию включить:

1. Запуск агента из терминала.
2. Выбор рабочей директории и модели через CLI или конфигурацию.
3. Подключение к LiteLLM через OpenAI-compatible HTTP API.
4. Единые типы сообщений, запросов, ответов и tool calls.
5. Цикл агента: отправить сообщения модели, распознать текст или вызов инструмента, выполнить инструмент, добавить результат в историю и продолжить.
6. Инструменты `read_file`, `write_file`, `list_directory`, `search`.
7. Базовая сессия с UUID, рабочей директорией, моделью и историей сообщений.
8. Интерактивный REPL.
9. Безопасность путей и ограничение доступа рабочей директорией.
10. Обработка ошибок, логирование и тесты.

В MVP не включать UI, сложное планирование задач, автономный запуск команд без подтверждения, базу данных и multi-agent режим.

Важно: этот проект является учебным. Поэтому реализация должна идти не только по функциональным слоям, но и по уровню сложности Rust. Нельзя перескакивать сразу к полноценному агентскому циклу: каждый следующий этап должен опираться на рабочий и понятный предыдущий этап.

Каждый этап считается завершённым только после выполнения четырёх условий:

1. Код реализован и запускается.
2. Добавлены тесты для изученных сценариев.
3. Написана учебная документация по этапу.
4. Код снабжён понятными комментариями и Rust-документацией там, где это необходимо.

Главный учебный маршрут:

```text
базовый Rust
    -> модули и типы
    -> CLI
    -> ошибки
    -> файлы и безопасность путей
    -> async/Tokio
    -> HTTP и JSON
    -> абстракции provider
    -> session/history
    -> tools и registry
    -> agent loop
    -> тестирование и production-практики
```

## 11. Этап 6. Общий интерфейс tools

### Файлы

- `src/tools/mod.rs`;
- `src/tools/types.rs`.

Определить trait:

```rust
#[async_trait]
pub trait Tool: Send + Sync {
    fn name(&self) -> &'static str;
    fn description(&self) -> &'static str;
    fn parameters_schema(&self) -> serde_json::Value;
    async fn execute(
        &self,
        args: serde_json::Value,
        context: &ToolContext,
    ) -> Result<ToolResult, AppError>;
}
```

`ToolContext` содержит абсолютную рабочую директорию, режим подтверждения, лимиты размера файла/результата и tracing context.

`ToolResult` содержит success/error, текст для модели, optional structured data и признак truncation.

### Registry

`ToolRegistry` должен:

1. регистрировать инструменты по snake_case имени;
2. строить `ToolDefinition` для LLM;
3. находить tool по имени;
4. валидировать имя и аргументы;
5. возвращать структурированную ошибку неизвестного инструмента.

## 16. Этап 11. Агентский цикл

### Файл

- `src/agent.rs`.

Алгоритм:

```text
добавить user message в Session
повторять не более max_tool_rounds:
    отправить историю + definitions tools в LLM
    если обычный текст без tool calls:
        добавить assistant message
        вернуть текст
    если tool calls:
        добавить assistant message с tool calls
        для каждого вызова:
            распарсить JSON arguments
            найти tool в registry
            выполнить tool
            добавить tool message с результатом
        продолжить цикл
    если ответ некорректен:
        вернуть диагностическую ошибку
если достигнут лимит:
    вернуть сообщение о превышении лимита
```

Обязательно:

1. Защита от бесконечных вызовов через `max_tool_rounds`.
2. Сохранение assistant message перед tool result.
3. Сохранение `tool_call_id`.
4. Поддержка нескольких вызовов в одном ответе.
5. Ошибку инструмента передавать модели как tool result, если восстановление возможно.
6. Запрет инструменту менять рабочую директорию.
7. Логирование имени, длительности и статуса без секретов и полных содержимых файлов.

Сделать fake provider, возвращающий последовательно `list_directory`, `read_file`, финальный текст, и проверить историю.

Ниже приведена отдельная последовательность именно для изучения Rust. Она важнее скорости получения готового агента: на каждом уровне сначала нужно понять язык и применённые конструкции, а затем использовать их в проекте.

### Цель

Научиться компилировать Rust-программы, работать с `fn main`, переменными, типами, строками, коллекциями, условиями, циклами и `Result`.

# 28. Стандарт комментариев в исходном коде

Код должен быть хорошо прокомментирован, но комментарии обязаны объяснять причины и инварианты, а не повторять синтаксис.

## 28.1. Комментарии модулей

В начале каждого сложного модуля использовать `//!`:

```rust
//! Реализация безопасной работы с файлами внутри рабочей директории.
//!
//! Все публичные операции проходят через проверку пути. Это необходимо,
//! чтобы пользовательский ввод не позволил инструменту выйти за пределы
//! разрешённого workspace.
```

## 28.2. Rustdoc публичного API

Каждый публичный элемент документировать так:

```rust
/// Читает часть текстового файла внутри рабочей директории.
///
/// # Errors
///
/// Возвращает ошибку, если путь находится за пределами workspace,
/// файл недоступен или превышен лимит размера.
///
/// # Security
///
/// Путь нельзя использовать для доступа к файлам выше `working_dir`.
pub async fn read_file(...) -> Result<ToolResult, AppError> {
    // Реализация...
}
```

## 28.3. Что обязательно объяснять обычными комментариями

Добавлять `//` или `/* ... */`, когда код содержит:

- нетривиальную проверку безопасности;
- преобразование ownership или lifetime;
- необычный `Arc`, `Mutex`, `Box` или `dyn Trait`;
- порядок добавления сообщений в историю;
- обработку нескольких tool calls;
- атомарную запись;
- обход symlink/path traversal;
- ограничение размера ответа;
- причину выбора blocking или async API;
- workaround для особенности стороннего API.

## 28.4. Чего избегать

Не писать бесполезные комментарии вроде:

```rust
// Увеличиваем счётчик
counter += 1;
```

Вместо этого объяснять инвариант:

```rust
// Увеличиваем счётчик именно после завершения tool call,
// чтобы одна итерация модели не считалась выполненной дважды.
counter += 1;
```

## 28.5. Комментарии для учебного проекта

На учебных этапах допустимы более подробные комментарии, чем в production-коде. Для сложных функций использовать структуру:

1. что функция получает;
2. что проверяет;
3. какое состояние изменяет;
4. что возвращает;
5. какие ошибки возможны;
6. почему порядок операций важен.

После завершения этапа комментарии нужно перечитать и удалить только дублирующие комментарии, не удаляя объяснения концепций Rust и безопасности.

# 29. Правила обучения и реализации

1. Не использовать новый crate, пока не объяснено, какую проблему он решает.
2. Не скрывать логику за helper-функцией без документации её контракта.
3. Не применять `unwrap()` и `expect()` в коде, который обрабатывает пользовательский ввод, сеть или файлы.
4. Для каждого нового trait сначала написать короткое объяснение, зачем он нужен.
5. Для каждого async-модуля объяснить, почему он async.
6. Для каждой структуры объяснить, кто владеет её данными.
7. После каждого этапа запускать форматирование, компиляцию и соответствующие тесты.
8. Не объединять несколько крупных учебных концепций в один незадокументированный коммит.
9. Сначала реализовать простую синхронную версию алгоритма, затем усложнять её только при необходимости.
10. Сохранять рабочее состояние проекта после каждого этапа.
11. Не переходить к следующему этапу, пока не понятны ошибки и решения текущего.
12. Любое упрощение MVP явно фиксировать в документации как ограничение.

# 30. Формат коммита для учебного этапа

Каждый этап оформлять отдельным коммитом или небольшой группой связанных коммитов:

```text
feat(stage-01): introduce basic rust domain types
docs(stage-01): explain ownership and result handling
test(stage-01): cover basic domain functions
```

В описании коммита или сопроводительной заметке указывать:

- какую Rust-концепцию изучали;
- какие файлы изменились;
- какие тесты добавлены;
- какие ограничения остались;
- что будет реализовано дальше.

# 31. Финальный учебный Definition of Done

Проект можно считать завершённым как учебный MVP, если:

- [ ] каждый учебный этап имеет отдельную заметку в `docs/learning/`;
- [ ] каждая заметка содержит теорию, практику, тесты, ошибки и критерии завершения;
- [ ] сложные модули содержат `//!`-документацию;
- [ ] публичные типы, traits и методы имеют Rustdoc;
- [ ] сложная логика объясняет причины и инварианты комментариями;
- [ ] код не содержит необоснованных `unwrap()`/`expect()`;
- [ ] каждая новая Rust-концепция используется в отдельной понятной задаче;
- [ ] `cargo fmt -- --check` проходит;
- [ ] `cargo check` проходит;
- [ ] `cargo test` проходит;
- [ ] `cargo clippy --all-targets --all-features -- -D warnings` проходит;
- [ ] README объясняет запуск проекта;
- [ ] пользователь может проследить путь от простого CLI до agent loop по истории коммитов и учебным заметкам;
- [ ] весь потенциально опасный код имеет комментарий с объяснением security rationale;
- [ ] после чтения документации другой студент может продолжить реализацию без устного сопровождения.
